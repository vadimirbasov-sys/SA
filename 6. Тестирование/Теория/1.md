# Лекция: Тестирование программного обеспечения — виды, уровни и практические примеры

---

## 1. Введение в тестирование ПО

Тестирование программного обеспечения — это процесс проверки соответствия разработанного продукта заявленным требованиям, ожиданиям пользователей и стандартам качества. Основная цель тестирования — выявить дефекты до передачи продукта в эксплуатацию, а также предоставить заинтересованным сторонам объективную информацию о текущем уровне качества.

Чтобы системно подойти к проверке сложной информационной системы, в индустрии принято классифицировать тесты по нескольким осям:
- **по уровню детализации и близости к коду** (модульное, интеграционное, системное, приёмочное);
- **по типу проверяемых свойств** (функциональное, нефункциональное);
- **по цели и месту в процессе разработки** (smoke-тесты, регрессионные, приёмочные и др.).

В этой лекции мы подробно разберём ключевые понятия, научимся отличать уровни тестирования от типов и рассмотрим конкретные примеры тест-кейсов для каждого вида.

---

## 2. Уровни тестирования: от класса к бизнес-процессу

Классическая модель представляет тестирование в виде пирамиды, где основание составляют быстрые и изолированные модульные тесты, а на вершине — небольшое количество сквозных дорогостоящих проверок. Уровни выделяются в зависимости от масштаба тестируемого компонента и фазы разработки.

### 2.1. Модульное тестирование (Unit Testing)

**Определение**  
Модульное тестирование проверяет корректность работы наименьших автономно тестируемых частей программы — функций, методов, классов. Один unit-тест взаимодействует только с тестируемым модулем, все внешние зависимости (базы данных, файловая система, сеть, другие классы) заменяются заглушками (mock/stub).

**Кто выполняет**  
Разработчик, сразу после написания кода. Тесты запускаются автоматически при каждой сборке.

**Цели**
- Убедиться, что логика отдельного компонента работает правильно.
- Быстро получить обратную связь о регрессии.
- Служить живой документацией к API модуля.

**Инструменты**  
JUnit, NUnit, pytest, Jest, Mocha и др.

**Пример (псевдокод)**
```
class Cart:
    def add_item(self, item, quantity):
        ...

def test_add_item_increases_quantity():
    cart = Cart()
    cart.add_item("book", 1)
    assert cart.total_items() == 1
```

### 2.2. Интеграционное тестирование (Integration Testing)

**Определение**  
Интеграционные тесты проверяют взаимодействие между несколькими модулями, компонентами или внешними сервисами. В отличие от unit-тестов, здесь используются реальные связи — модули, базы данных, очереди сообщений, API — но окружение всё ещё может быть ограниченным (например, тестовая БД вместо продакшен-кластера).

**Виды интеграционного тестирования**
- **Компонентное интеграционное тестирование** — взаимодействие модулей внутри одного приложения.
- **Системно-интеграционное тестирование** — взаимодействие между независимыми системами (микросервисами, платёжными шлюзами, CRM).

**Кто выполняет**  
Разработчики или автоматизаторы тестирования. Часть выполняется в CI-пайплайне.

**Цели**
- Убедиться, что контракты между модулями соблюдаются.
- Выявить ошибки сериализации, передачи параметров, обработки ответов.
- Проверить корректность работы с драйверами БД, брокерами сообщений.

**Пример**  
Тест, проверяющий, что сервис корзины, при вызове метода `addItem`, корректно сохраняет запись в базе данных и возвращает обновлённое количество товаров. Здесь реально поднимается тестовая БД.

### 2.3. Системное тестирование (System Testing)

**Определение**  
Это тестирование полностью интегрированной системы на соответствие функциональным и нефункциональным требованиям. Системное тестирование выполняется на окружении, максимально приближенном к продуктивному, и не требует знания внутренней структуры кода (тестирование через пользовательские интерфейсы или публичные API).

**Кто выполняет**  
Отдельная команда тестирования или QA-инженеры.

**Цели**
- Проверить поведение всей системы в условиях, близких к реальным.
- Оценить соответствие системы исходным спецификациям.
- Проверить сквозные сценарии (end-to-end).

**Включает**
- Функциональное системное тестирование (проверка бизнес-логики через UI/API).
- Нефункциональное (производительность, безопасность, удобство использования).

### 2.4. Приёмочное тестирование (Acceptance Testing)

**Определение**  
Финальный этап, на котором заказчик или конечные пользователи (UAT — User Acceptance Testing) определяют, готова ли система к промышленной эксплуатации. Критерий приёмки формулируется на основе бизнес-требований.

**Виды приёмочного тестирования**
- **Альфа-тестирование** — внутреннее, выполняется в организации разработчика сотрудниками, не входящими в команду разработки.
- **Бета-тестирование** — внешнее, выполняется ограниченной группой реальных пользователей на их собственных данных.
- **UAT (User Acceptance Testing)** — формализованные сценарии, повторяющие реальные действия конечных пользователей, часто проверяет соответствие бизнес-процессам.

**Кто выполняет**  
Представители заказчика, бизнес-аналитики, конечные пользователи под руководством QA-команды.

**Цели**
- Подтвердить, что продукт решает задачи бизнеса.
- Получить подпись заказчика о готовности системы.

## 3. Типы тестирования: что именно проверяем

Помимо уровня, каждый тест имеет тип, отражающий **какую именно характеристику** системы мы оцениваем. Наиболее фундаментальное деление — функциональное и нефункциональное тестирование.

### 3.1. Функциональное тестирование (Functional Testing, FT)

**Сущность**  
Проверка того, **что** система делает. Функциональные тесты нацелены на верификацию поведения системы, описанного в функциональных требованиях, пользовательских историях, спецификациях.

**Характеристика**  
- На вход подаются определённые данные.
- Выполняется действие (через UI, API или вызов метода).
- Полученный результат сравнивается с ожидаемым.

**Где встречается**  
Функциональное тестирование не привязано строго к одному уровню:
- *Unit-уровень*: тестируется логика одного публичного метода.
- *Integration-уровень*: проверяется корректность бизнес-операции, затрагивающей несколько сервисов.
- *System-уровень*: тестируются пользовательские сценарии через графический интерфейс.
- *Acceptance-уровень*: бизнес-тесты, реализующие приёмочные критерии.

**Примеры вопросов, на которые отвечает FT**
- Добавляется ли товар в корзину при нажатии кнопки «Купить»?
- Возвращает ли API корректный HTTP-статус и тело ответа?
- Рассчитывается ли скидка согласно бизнес-правилам?

Таким образом, термин «функциональное тестирование» часто используют, подразумевая именно проверку бизнес-функций на системном уровне, но методологически оно применимо везде.

### 3.2. Интеграционное тестирование (как тип и как уровень)

Здесь может возникнуть терминологическая двойственность: мы уже описали интеграционное тестирование как **уровень**. Однако часто говорят об интеграционных тестах как о **типе**, фокусирующемся на корректности связей. С точки зрения классификации по ISTQB, интеграционное тестирование — это именно **уровень**, а проверка взаимодействий может быть и функциональной, и нефункциональной (например, тестирование пропускной способности интеграционного канала — это нефункциональный аспект).

В контексте нашей лекции, когда мы употребляем «интеграционное тестирование» (IT), мы имеем в виду проверку интерфейсов между компонентами с целью выявления дефектов в их взаимодействии.

## 4. Бизнес-тестирование (End-to-End / UAT-like)

Под «бизнес-тестированием» в практике часто понимают тесты, моделирующие **полноценные бизнес-процессы** пользователя от начала до конца, с минимальным количеством моков и замен. Синонимы: end-to-end тесты (E2E), сквозные тесты, часто именно они ложатся в основу UAT-сценариев.

**Цель**  
Проверить, что несколько подсистем, работая совместно, выдают ожидаемый с точки зрения бизнеса результат. Это самый высокоуровневый вид тестирования, близкий к реальному использованию.

**Пример бизнес-процесса для интернет-магазина**  
1. Пользователь заходит на сайт, выполняет поиск товара.  
2. Добавляет товар в корзину.  
3. Переходит к оформлению заказа, выбирает адрес доставки.  
4. Оплачивает заказ.  
5. Получает подтверждение на email.  

E2E-тест прогоняет всю цепочку, используя реальный браузер (или API-вызовы последовательно) и проверяет, что на каждом шаге система реагирует верно и данные не теряются.

**Связь с UAT**  
UAT, или приёмочное тестирование пользователем, по сути, есть подмножество E2E-тестов, которые дополнительно оцениваются с точки зрения удобства и соответствия реальным рабочим процессам. Часто именно E2E-сценарии, покрывающие критически важные бизнес-процессы, предъявляются заказчику на финальной демонстрации.

**Особенности**
- Медленные, требуют развёрнутого окружения.
- Относительно хрупкие (могут ломаться из-за незначительных изменений UI).
- Их количество должно быть ограничено (см. пирамиду тестирования).

## 5. Smoke-тесты (дымовые тесты)

**Определение**  
Smoke-тестирование — это короткий набор тестов, направленный на проверку того, что самые основные функции приложения работают и система в целом «не дымится» после сборки или развёртывания. Это «тесты на вшивость»: если smoke провален, дальнейшее тестирование бессмысленно, билд отклоняется.

**Место в процессе**  
- После развёртывания новой версии на тестовом стенде.
- В CI/CD-конвейере сразу после деплоя.
- Перед передачей на полноценное системное тестирование.

**Характеристика**  
- Минимальный набор (5–10 тестов на главные сценарии).
- Должен выполняться быстро (минуты, не часы).
- Полностью автоматизирован.

**Примеры smoke-проверок для интернет-магазина**
1. Главная страница открывается (HTTP 200).
2. Форма авторизации позволяет войти под валидным пользователем.
3. Поиск по ключевому слову возвращает непустой список.
4. Корзина доступна и показывает 0 товаров для нового пользователя.

Если хотя бы одна из этих проверок падает — сборка считается неработоспособной.

**Отличие от Sanity-тестирования**  
Sanity-тесты узконаправлены: проверяют, что конкретная исправленная функция или небольшая доработка работает правильно, не углубляясь в остальную систему. Smoke же покрывает широкий «дымовой» контур критического функционала.

## 6. Примеры тест-кейсов по видам тестирования

Для иллюстрации возьмём гипотетическую систему — интернет-магазин «ТехноЛавка». Рассмотрим одну функцию **«Добавление товара в корзину»** и покажем, как она тестируется на разных уровнях и в разных типах.

### 6.1. Модульный (Unit) тест-кейс

**Объект**: метод `addItem(itemId, quantity)` класса `ShoppingCart`.  
**Окружение**: все зависимости замоканы. Тест выполняется в памяти.

| Поле                | Описание                                                                 |
|---------------------|--------------------------------------------------------------------------|
| **ID**              | UT-CART-01                                                               |
| **Название**        | Увеличение количества существующей позиции в корзине                      |
| **Предусловия**     | Создан экземпляр корзины. В корзине уже есть товар `itemId=42` в кол-ве 2.|
| **Шаги**            | 1. Вызвать `cart.addItem(42, 3)`.                                       |
| **Ожидаемый результат** | Метод возвращает `true`. Общее количество единиц товара 42 становится равным 5. Метод `getTotalQuantity()` возвращает 5. Никакие внешние сервисы не были вызваны. |

### 6.2. Интеграционный тест-кейс (сервис + БД)

**Объект**: интеграция `CartService` и реальной тестовой БД PostgreSQL.  
**Окружение**: поднята тестовая БД с таблицей `cart_items`.

| Поле                | Описание                                                                                 |
|---------------------|------------------------------------------------------------------------------------------|
| **ID**              | IT-CART-01                                                                               |
| **Название**        | Сохранение позиции в БД через сервис корзины                                              |
| **Предусловия**     | БД чиста. Пользователь с `user_id=100` аутентифицирован.                                 |
| **Шаги**            | 1. Вызвать `cartService.addItem(userId=100, itemId=55, quantity=2)`.                      |
|                     | 2. Выполнить прямой SQL-запрос: `SELECT quantity FROM cart_items WHERE user_id=100 AND item_id=55`. |
| **Ожидаемый результат** | Сервис возвращает объект `CartStatus` со свойством `success=true`. SQL-запрос возвращает запись с `quantity=2`. При повторном вызове с тем же `itemId` количество обновляется (инкрементируется), а не создаётся дубликат. |

### 6.3. Системный функциональный тест-кейс (UI)

**Объект**: пользовательский интерфейс интернет-магазина.  
**Окружение**: тестовый стенд с развёрнутым приложением, браузер.

| Поле                | Описание                                                                                                     |
|---------------------|--------------------------------------------------------------------------------------------------------------|
| **ID**              | ST-CART-02                                                                                                   |
| **Название**        | Отображение добавленного товара в мини-корзине                                                                |
| **Предусловия**     | Пользователь авторизован. Открыта страница товара с `itemId=10`.                                             |
| **Шаги**            | 1. Нажать кнопку «Добавить в корзину».                                                                       |
|                     | 2. Дождаться появления попапа «Товар добавлен».                                                              |
|                     | 3. Навести курсор на иконку корзины в шапке сайта (открыть мини-корзину).                                    |
| **Ожидаемый результат** | В мини-корзине отображается одна позиция с названием товара, ценой и количеством = 1. Сумма корзины корректна. |

### 6.4. End-to-End / UAT тест-кейс (бизнес-сценарий)

**Объект**: сквозной процесс «Покупка товара зарегистрированным пользователем».  
**Окружение**: предпродуктивный стенд, идентичный продуктиву, реальные email-сервисы, платёжный шлюз в тестовом режиме.

| Поле                | Описание                                                                                                                                         |
|---------------------|--------------------------------------------------------------------------------------------------------------------------------------------------|
| **ID**              | E2E-PURCHASE-01                                                                                                                                  |
| **Название**        | Успешная оплата заказа с доставкой курьером                                                                                                      |
| **Предусловия**     | Пользователь `buyer@example.com` зарегистрирован, адрес доставки добавлен. Товар «Ноутбук» в наличии. Баланс тестовой платёжной карты достаточен. |
| **Шаги**            | 1. Войти под `buyer@example.com`.                                                                                                                |
|                     | 2. Найти «Ноутбук» через поиск.                                                                                                                  |
|                     | 3. Добавить товар в корзину.                                                                                                                     |
|                     | 4. Перейти в корзину, нажать «Оформить заказ».                                                                                                   |
|                     | 5. Выбрать адрес, способ доставки «Курьер», подтвердить.                                                                                         |
|                     | 6. Ввести данные тестовой карты, оплатить.                                                                                                       |
|                     | 7. Дождаться страницы подтверждения.                                                                                                             |
| **Ожидаемый результат** | Заказ создан в статусе «Оплачен». На email приходит письмо с деталями заказа. В админке магазина заказ виден. В истории пользователя заказ присутствует. |

Этот же кейс с небольшими правками может использоваться как **UAT-тест**, если его выполняет представитель заказчика и проверяет корректность писем, печатных форм, удобство интерфейса.

### 6.5. Smoke-тест-кейс

**Объект**: минимальный набор критичных функций, проверяемый после деплоя.  
**Окружение**: staging-стенд.

| Поле                | Описание                                                                                   |
|---------------------|--------------------------------------------------------------------------------------------|
| **ID**              | SMOKE-01                                                                                   |
| **Название**        | Дымовая проверка доступности ключевых страниц и базового функционала                        |
| **Предусловия**     | Стенд развёрнут, тестовый пользователь существует.                                          |
| **Шаги**            | 1. GET / — получить главную страницу (200 OK).                                             |
|                     | 2. POST /api/login с валидными креденшелами — получить токен.                              |
|                     | 3. GET /api/products?search=phone — список товаров непуст.                                 |
|                     | 4. POST /api/cart/add — добавить товар, получить 200.                                      |
| **Ожидаемый результат** | Все запросы завершаются успешно, страницы отображаются без критических ошибок.           |

Этот тест можно автоматизировать и запускать за 30 секунд. Упавший smoke означает, что основные подсистемы не работают, и команда должна срочно чинить инцидент, не тратя время на детальное тестирование.

## 7. Взаимосвязь: пирамида тестирования и здравый смысл

На практике ни один вид тестирования не применяется изолированно. Эффективная стратегия опирается на **пирамиду тестирования**:

1. **Основание — модульные тесты**. Быстрые, изолированные, покрывают логику. Их много, они выполняются при каждом коммите.
2. **Средний слой — интеграционные тесты**. Проверяют связки, API, работу с БД. Количество меньше, чем unit-тестов, выполняются в CI.
3. **Верхний слой — системные/приёмочные/E2E тесты**. Медленные, проверяют полные бизнес-процессы. Их мало, запускаются реже (ночь или перед релизом).

Smoke-тесты находятся на стыке: они могут быть и интеграционными, и высокоуровневыми, но обязательно выполняются первыми при любом серьёзном изменении окружения.

---

## Заключение

Понимание классификации тестирования позволяет грамотно планировать процесс обеспечения качества, оптимизировать затраты времени и ресурсов и выстраивать надёжный пайплайн поставки. Модульные тесты дают быструю обратную связь разработчику, интеграционные ловят рассогласование интерфейсов, системные и бизнес-тесты подтверждают, что продукт готов решать реальные задачи пользователя. Smoke-тесты, в свою очередь, являются «стражей ворот», предотвращающей попадание заведомо неработоспособных сборок на следующие этапы. Комбинация всех этих видов, разумно распределённая по пирамиде, — фундамент зрелого процесса разработки.
