Это пятая и завершающая лекция цикла, посвященная **низкоуровневой детализации**: от LLD до кода, API-контрактов и тестов. Мы наконец спускаемся с небес бизнес‑требований и пользовательских сценариев в **инженерные артефакты**, которые непосредственно ложатся в основу репозитория и CI/CD.

# Лекция: От FSD к коду – LLD, API‑контракты и тесты как живая документация

## 1. Где мы сейчас и куда идём

Мы прошли путь:
- **BRD** — определили бизнес‑ценность и цели (зачем мы строим кофейный предзаказ).
- **SRS** — описали системные требования, API, данные и состояния (что система должна делать).
- **FSD** — детализировали поведение каждого экрана, валидацию, ошибки и переходы (как пользователь взаимодействует).

Теперь настало время **реализации**. Здесь документация меняет свой характер: она становится максимально конкретной, машинно‑читаемой и тесно связанной с кодом.

**Главная задача этого этапа** — обеспечить:
- единое понимание архитектуры внутри команды разработки;
- чёткий контракт между фронтендом и бэкендом (API);
- возможность автоматической проверки, что система работает согласно требованиям (тесты).

В этой лекции мы разберём три кита реализации:
1. **LLD (Low‑Level Design)** — внутреннее устройство классов, БД и алгоритмов.
2. **API‑контракты (OpenAPI / gRPC)** — спецификация интерфейсов между сервисами.
3. **Тесты (unit, integration, e2e)** — код, который доказывает, что система корректна и останется такой в будущем.

---

## 2. LLD (Low‑Level Design) – архитектура на уровне классов и таблиц

### 2.1. Что такое LLD и для кого он

**LLD (Low‑Level Design)** – это документ (или набор артефактов), который описывает:
- структуру базы данных (ER‑диаграммы, схемы таблиц, индексы);
- иерархию классов, интерфейсов и их методы (UML‑диаграммы);
- ключевые алгоритмы (псевдокод или блок‑схемы);
- взаимодействие между модулями (диаграммы последовательностей).

**Аудитория:** backend‑разработчики, DBA, архитекторы, а также senior‑разработчики, которые будут писать код по этому плану.

LLD обычно создаётся на основе SRS, но уже с учётом выбранного технологического стека (Java + Spring, Python + Django, PostgreSQL, Redis и т.д.).

### 2.2. Структура LLD на примере нашего сервиса заказов

#### 2.2.1. ER‑диаграмма (схема БД)

Мы проектируем базу данных для хранения заказов, клиентов, товаров и точек выдачи.

```
+----------------+       +------------------+
|    clients     |       |     orders        |
+----------------+       +------------------+
| id (PK)        |<------| client_id (FK)    |
| phone          |       | id (PK)           |
| name           |       | total_amount      |
| created_at     |       | status (enum)     |
+----------------+       | point_id (FK)     |
                         | created_at        |
                         | updated_at        |
                         +------------------+
                               |
                               | (1 : N)
                               v
                      +------------------+
                      | order_items      |
                      +------------------+
                      | id (PK)          |
                      | order_id (FK)    |
                      | product_id (FK)  |
                      | quantity         |
                      | price_per_unit   |
                      | modifiers (json) |
                      +------------------+
```

**Важные решения в LLD:**
- Для `status` используем `ENUM` в БД (или отдельную таблицу-справочник, если статусов много и они могут меняться).
- Для модификаторов (сироп, молоко) используем JSON-поле, чтобы не плодить таблицы под каждый вариант – гибко и быстро.
- Добавляем индексы по `client_id` и `status` для быстрых запросов «показать все заказы пользователя» или «все заказы в статусе PENDING».

#### 2.2.2. Диаграмма классов (упрощённая)

На бэкенде мы выделяем слои:
- **Controller** – принимает HTTP‑запросы, валидирует входные данные.
- **Service** – бизнес‑логика (расчёт стоимости, проверка резерва, переход статусов).
- **Repository** – доступ к БД (CRUD).

Пример класса `OrderService` (псевдокод на Java):

```java
public class OrderService {
    private OrderRepository orderRepo;
    private ProductRepository productRepo;
    private PaymentGateway paymentGateway;

    public Order createOrder(OrderRequest request) {
        // 1. Проверить, что все товары есть в наличии
        // 2. Рассчитать итоговую сумму
        // 3. Зарезервировать товары на 10 минут
        // 4. Сохранить заказ со статусом PENDING_PAYMENT
        // 5. Вернуть объект Order с id и статусом
    }

    public void confirmPayment(Long orderId, PaymentResult result) {
        // Если оплата успешна – перевести статус в PAID
        // Если нет – отменить резерв и перевести в CANCELLED
    }
}
```

В LLD мы детально описываем сигнатуры методов, исключения, которые они могут бросать, и взаимодействие с другими сервисами (например, вызов внешнего платежного шлюза).

#### 2.2.3. Алгоритм расчёта стоимости

Опишем псевдокодом:

```
function calculateTotal(cartItems):
    total = 0
    for each item in cartItems:
        basePrice = getProductPrice(item.productId)
        modifiersPrice = sum(modifier.price for modifier in item.modifiers)
        total += (basePrice + modifiersPrice) * item.quantity
    return total
```

В LLD мы также указываем, что цена должна пересчитываться **на сервере**, а не доверять клиенту (чтобы избежать подделки суммы).

## 3. API‑контракты (OpenAPI / Swagger) – документация интерфейсов

### 3.1. Зачем нужен API‑контракт

API‑контракт – это спецификация, которая описывает все эндпоинты, их параметры, заголовки, тела запросов и ответов, коды ошибок. Это **единый источник правды** для фронтенда, мобильных приложений и внешних интеграторов.

Главные преимущества:
- **Параллельная разработка** – фронтенд может разрабатывать, используя моки (например, MockServer) на основе контракта, не дожидаясь бэкенда.
- **Автоматическая генерация клиентских SDK** (Swagger Codegen, OpenAPI Generator).
- **Встроенная документация** – Swagger UI позволяет тестировать API прямо из браузера.
- **Валидация запросов** – можно проверять соответствие контракту на уровне gateway.

### 3.2. Пример спецификации (OpenAPI 3.0) для создания заказа

```yaml
openapi: 3.0.0
info:
  title: Coffee Pre-order API
  version: 1.0.0
paths:
  /api/v1/orders:
    post:
      summary: Создать новый заказ
      operationId: createOrder
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required:
                - items
                - pointId
              properties:
                items:
                  type: array
                  items:
                    type: object
                    required:
                      - productId
                      - quantity
                    properties:
                      productId:
                        type: integer
                      quantity:
                        type: integer
                        minimum: 1
                      modifiers:
                        type: array
                        items:
                          type: string
                        description: Идентификаторы допов (сироп, молоко)
                pointId:
                  type: integer
                promoCode:
                  type: string
      responses:
        '201':
          description: Заказ создан
          content:
            application/json:
              schema:
                type: object
                properties:
                  orderId:
                    type: string
                    format: uuid
                  status:
                    type: string
                    enum: [PENDING_PAYMENT]
                  totalAmount:
                    type: number
                    format: double
        '400':
          description: Ошибка валидации (например, нет товаров)
        '404':
          description: Точка выдачи не найдена
        '409':
          description: Товара нет в наличии или конфликт резерва
```

**Что важно в контракте:**
- Чётко указаны обязательные поля (`required`).
- Ограничения (минимальное количество, формат).
- Все возможные HTTP‑коды и структуры ошибок.

### 3.3. Версионирование API

Мы включили версию в URL: `/api/v1/orders`. При изменении контракта (например, добавление нового поля) мы создаём `v2`, а `v1` поддерживаем какое‑то время для обратной совместимости.

### 3.4. Инструменты

- **Swagger Editor** – написание YAML/JSON.
- **Swagger UI** – визуализация и тестирование.
- **Postman** – импорт контракта и создание коллекций тестов.
- **SpringDoc / OpenAPI‑generator** – генерация кода из спецификации.

## 4. Тесты – документация, которая не врёт

### 4.1. Почему тесты – это тоже документация

Тесты (особенно автоматические) являются **живой документацией** – они всегда актуальны, потому что выполняются в CI. Если тест падает, код не попадает в продакшен. Хорошо написанные тесты показывают, как должен использоваться тот или иной компонент, какие ожидаются входы и выходы.

Мы выделяем три уровня тестирования:

#### 4.1.1. Unit‑тесты (проверка одного класса)

- Проверяют методы в изоляции (мокают зависимости).
- Пример: тест метода `calculateTotal` в `OrderService`.
- Пишутся разработчиками на том же языке (JUnit, pytest, Jest).

```java
@Test
void testCalculateTotal_withModifiers() {
    CartItem item = new CartItem(productId=1, quantity=2, modifiers=["syrup1"]);
    when(productRepo.getPrice(1)).thenReturn(100.0);
    when(modifierRepo.getPrice("syrup1")).thenReturn(20.0);
    double total = orderService.calculateTotal(List.of(item));
    assertEquals(240.0, total, 0.001);
}
```

#### 4.1.2. Интеграционные тесты

- Проверяют взаимодействие с БД, внешними сервисами, очередями.
- Например, тест создания заказа с реальным репозиторием (но с тестовой БД).
- Могут использовать Testcontainers для эмуляции зависимостей.

#### 4.1.3. E2E‑тесты (сквозные)

- Проверяют полный пользовательский сценарий: от HTTP‑запроса до ответа, включая все внешние системы (платежи, SMS).
- Часто используют Postman/Newman, Cypress, Selenium или специальные фреймворки.
- Пример: «Пользователь отправляет POST /orders, система возвращает 201, затем мы проверяем в БД, что заказ сохранился с правильным статусом».

### 4.2. Связь тестов с требованиями (Traceability)

Каждый тест‑кейс должен ссылаться на ID требования из SRS или FSD. Например:

```
Тест: TC-001 (SRS-02.01) – Проверка валидации телефона
- Отправить неверный номер -> получить 400 с кодом VALIDATION_PHONE
```

Эта матрица позволяет быстро понять, какое требование покрыто тестами, а какое – нет.

### 4.3. Тесты как документация в коде

Используйте **BDD** (Behavior‑Driven Development) с фреймворками типа Cucumber или SpecFlow. Тогда тесты пишутся на естественном языке:

```
Feature: Создание заказа
  Scenario: Успешное создание с корректными данными
    Given клиент с номером +7 999 111 22 33
    And корзина содержит 2 товара
    When он нажимает "Оформить"
    Then заказ создаётся со статусом PENDING_PAYMENT
    And сохраняется в БД
```

Такой сценарий читается бизнесом и одновременно является исполняемым тестом.

## 5. Автоматизация документации – делаем её живой

Чтобы документация не устаревала, мы внедряем практику **документация как код**:

1. **API‑контракт** хранится в репозитории и обновляется вместе с изменениями кода.
2. **Диаграммы** можно генерировать из аннотаций кода (например, PlantUML из Java-кода с помощью javadoc).
3. **Схема БД** управляется миграциями (Liquibase) – сам файл миграции является документацией структуры.
4. **Тесты** прогоняются в CI и отображают покрытие (Allure, ReportPortal) – это отчёт о том, что работает.

## 7. Типичные ошибки на этапе детализации

1. **LLD слишком детализированный или слишком абстрактный** – пишите ровно столько, чтобы разработчик мог начать писать код, не додумывая архитектуру, но не описывайте каждую локальную переменную.
2. **API‑контракт не синхронизируется с кодом** – используйте генерацию из кода (например, Springdoc) или валидацию контракта в CI.
3. **Тесты пишутся только после кода** – лучше писать их параллельно (TDD) или хотя бы до слияния в основную ветку.
4. **Игнорирование негативных тестов** – проверяйте не только «счастливый» путь, но и ошибки (401, 403, 404, 422).
5. **Документация разбросана по разным системам** – сведите всё в один репозиторий (код, тесты, контракт, миграции) для целостности.

## 8. Итоговая картина – как всё связано

| Этап | Артефакт | Форма | Назначение |
|------|----------|-------|------------|
| Бизнес | BRD | Текст, таблицы | Обоснование проекта |
| Система | SRS | Структурированный текст, диаграммы | Функциональные и нефункциональные требования |
| Пользователь | FSD | Макеты + спецификации состояний | Поведение интерфейса |
| Архитектура | LLD | ERD, UML, псевдокод | Внутреннее устройство классов и БД |
| Контракт | API Spec (OpenAPI) | YAML/JSON | Взаимодействие между компонентами |
| Проверка | Тесты (Unit/Integration/E2E) | Код (JUnit, pytest и др.) | Подтверждение корректности |

**Прослеживаемость:** каждый тест ссылается на SRS/FSD, каждый эндпоинт реализует требования из SRS, каждая таблица соответствует модели данных из LLD.
