# Лекция: Платежные технологии и системы  
## (на примере оплаты аренды сервера 3 390 ₽)

---

## 1. Введение: контекст и цель

**Кейс**: клиент (Дмитрий) арендует сервер в ООО «Облачный хостинг» и оплачивает заказ картой на сумму 3 390 ₽. Это классический **C2B-платёж** (Customer‑to‑Business): деньги движутся от держателя карты к мерчанту через цепочку банков-участников и платёжных систем.

**Проблема, которую решает аналитик**: часто клиент видит, что деньги списались, но в личном кабинете хостинга оплата не отображается — заказ остаётся в статусе `CREATED`, сервер не резервируется. Причина — **разрыв между авторизацией и клирингом/расчётом**.

**Цель лекции**:
- Понять, кто участвует в платеже (эмитент, эквайер, процессинг, платёжная система).
- Изучить жизненный цикл карточной транзакции: авторизация → клиринг → расчёт (settlement).
- Разобраться в особенностях национальных и международных платёжных систем (МИР, Visa, MasterCard, SWIFT).
- Узнать, как стандарты (ISO 8583, ISO 20022, PCI DSS) влияют на проектирование.
- Научиться проектировать статусную модель, события, интеграции и обработку задержек.

---

## 2. Основные участники платёжной системы

В любом карточном платеже задействованы пять ключевых ролей. В нашем кейсе они выглядят так:

| Роль | Кто это | Пример в кейсе аренды сервера |
|------|---------|-------------------------------|
| **Эмитент** | Банк, выпустивший карту клиента | Банк Дмитрия (например, Сбербанк) |
| **Эквайер** | Банк, обслуживающий торговую точку (мерчанта) | Банк ООО «Облачный хостинг» (например, Тинькофф) |
| **Процессинг** | Технологическая платформа для обработки транзакций | НСПК (для карт МИР) или международный процессинг (VisaNet, MasterCard) |
| **Платёжная система** | Организация, устанавливающая правила, маршруты и стандарты | МИР, Visa, MasterCard |
| **Мерчант** | Торговая точка (продавец товаров/услуг) | ООО «Облачный хостинг» |

**Важно**: аналитик должен чётко различать эти роли, так как каждая из них предъявляет свои требования к интеграциям, отчётности и обработке ошибок.

## 3. Платёжные системы и стандарты

### 3.1. SWIFT — международная система межбанковских сообщений

**SWIFT** — это не платёжная система, а **сеть для обмена финансовыми сообщениями** между банками. Она используется для международных переводов, валютных операций, аккредитивов.

**Как работает SWIFT (упрощённо)**:
1. Клиент банка А в России хочет перевести $1000 клиенту банка Б в Германии.
2. Банк А формирует сообщение **MT103** (тип «платеж клиента»).
3. Сообщение отправляется через защищённую сеть SWIFT.
4. Банк Б получает сообщение и зачисляет сумму получателю.
5. Расчёт (settlement) происходит через корреспондентские счета или клиринговые центры.

**Что делает системный аналитик при интеграции со SWIFT**:
- Проектирует API «SWIFT-платеж» → ядро → конвертер → SWIFT-шлюз.
- Согласует форматы (MT103 → JSON).
- Настраивает статусную модель: `SENT` → `CONFIRMED` → `FAILED`.
- Учитывает **cut-off time** (время окончания операционного дня).
- Добавляет аудит, ретраи при сбоях связи, AML и валютный контроль.

### 3.2. Национальная система платёжных карт «МИР»

**МИР** — российская национальная карточная платформа, управляемая НСПК. Работает по тем же принципам, что Visa/MasterCard, но полностью внутри России.

**Как работает МИР**:
1. Клиент оплачивает покупку картой МИР.
2. Терминал → эквайер → процессинг → НСПК → эмитент.
3. Эмитент авторизует платёж и возвращает ответ (Approved / Declined).
4. Через клиринг и расчёты происходит списание средств.

**Сравнение МИР и Visa/MasterCard**:

| Параметр | МИР | Visa / MasterCard |
|----------|-----|-------------------|
| Юрисдикция | Россия | Международная |
| Валюта расчётов | Рубли | USD/EUR/мультивалютная |
| Оператор | НСПК | Visa Inc. / Mastercard Inc. |
| Требования PCI DSS | Да | Да |
| Стандарт сообщений | ISO 8583 | ISO 8583 (для авторизации), ISO 20022 (для платёжных сообщений) |
| География | РФ / СНГ | Весь мир |
| Время расчёта | T+1 (рабочий день) | T+1…T+3 в зависимости от страны |

### 3.3. Международные стандарты: ISO 8583 и ISO 20022

- **ISO 8583** — стандарт для карточных сообщений (авторизация, клиринг). Используется всеми платёжными системами (Visa, MC, МИР). Сообщение содержит до 128 полей (например, PAN, сумма, код валюты, RRN, STAN).
- **ISO 20022** — более новый стандарт для финансовых сообщений (платежи, отчётность). С 2025 года обязателен для международных переводов через SWIFT. Позволяет передавать богатые структурированные данные.

**Для аналитика**: при проектировании интеграций нужно чётко знать, какие поля обязательны, как мапятся в JSON, какие коды ошибок используются.

## 4. Жизненный цикл карточной транзакции

Карточный платёж проходит три основных этапа. Важно понимать временные задержки на каждом этапе.

### 4.1. Этап 1 — Авторизация (Authorization)
- **Длительность**: 2–5 секунд (онлайн).
- **Суть**: проверка наличия средств, лимитов, антифрод. Банк-эмитент блокирует (hold) сумму на карте клиента. Деньги физически не списываются.
- **Результат**: код ответа (00 — успех, 05 — отклонение, 91 — таймаут и т.д.).
- **Что видит клиент**: «Оплата успешна», деньги «заморожены» (доступный баланс уменьшен).

### 4.2. Этап 2 — Клиринг (Clearing)
- **Длительность**: от нескольких часов до конца операционного дня (batch-обработка).
- **Суть**: мерчант (или эквайер) формирует файл всех транзакций за день и отправляет в платёжную систему. Платёжная система проверяет и подтверждает суммы, производит взаимозачёты между банками.
- **Результат**: формируются отчёты для эмитента и эквайера.
- **Что видит клиент**: в выписке может появиться «проводка в обработке», но фактического списания ещё нет.

### 4.3. Этап 3 — Расчёт (Settlement)
- **Длительность**: T+1 (следующий рабочий день) или T+2.
- **Суть**: через корреспондентские счета в Центральном банке происходит окончательное списание со счёта эмитента и зачисление на счёт эквайера. Затем эквайер зачисляет деньги мерчанту.
- **Результат**: деньги поступают на расчётный счёт ООО «Облачный хостинг».
- **Что видит клиент**: в выписке появляется окончательное списание.

### 4.4. Дополнительные операции
- **Reversal** — отмена авторизации (если операция не завершилась).
- **Refund** — возврат средств мерчантом клиенту.
- **Chargeback** — оспаривание платежа клиентом (возврат по инициативе банка).

### 4.5. Почему клиент видит «списано», а мерчант — ещё нет?

При авторизации банк-эмитент ставит холд (заморозку) на сумму. Эта сумма временно недоступна клиенту, но деньги ещё не покинули его счёт физически. Фактическое движение происходит на этапе settlement через корреспондентские счета ЦБ. Именно поэтому в личном кабинете аренды сервера оплата может отображаться с задержкой — статус заказа не обновится, пока не придёт подтверждение settlement.

### 4.6. График задержек по этапам

| Этап | Типичная задержка | Причина |
|------|-------------------|---------|
| Авторизация | 2–5 сек | Норма; при таймауте > 10 сек — Decline (код 91) |
| Формирование клиринг-батча | до конца операционного дня | Мерчант накапливает транзакции, отправляет по cut-off |
| Обработка в платёжной системе | 1–4 часа | Внутренняя валидация, сверки, маршрутизация |
| Settlement (ЦБ) | T+1 (рабочий день) | Расчёт через корсчета, не работает в выходные |
| Зачисление эквайером | +1–3 часа | Внутренние процессы банка-эквайера |

**Пример**: если клиент оплатил в понедельник утром, деньги на счёт хостинга поступят во вторник. Если оплата прошла в пятницу вечером — деньги придут во вторник-среду (выходные не считаются).

## 5. Клиринг и расчёты: схема движения денег

Ниже — упрощённая схема, показывающая, как деньги доходят до мерчанта.

```
Этап 1 — Авторизация (online, ~3 сек)
Клиент → эквайер → процессинг → платёжная система (МИР/Visa/MC) → эмитент
Эмитент проверяет баланс, лимиты, антифрод → возвращает код 00 (Approved)
Hold на карте клиента — деньги «заморожены».

Этап 2 — Клиринг (batch, T+0…T+1)
Мерчант формирует файл клиринга (транзакции за день) → отправляет в ПС.
ПС обрабатывает файл, проводит взаимозачёты между банками.
Подтверждение клиринга (ACK).

Этап 3 — Settlement (T+1…T+2)
Расчёт через корреспондентские счета в ЦБ:
- списание с корсчёта эмитента,
- зачисление на корсчёт эквайера,
- затем эквайер зачисляет деньги на расчётный счёт мерчанта.
```

**Ключевой момент**: мерчант получает деньги только после завершения settlement, а не после авторизации.

## 6. Процессинг — «сердце» карточных платежей

**Процессинг** — это технологическая платформа, которая:
- принимает запросы от POS-терминалов, интернет-магазинов, мобильных приложений;
- проверяет лимиты, антифрод, балансы;
- связывается с эмитентом/эквайером;
- обеспечивает авторизацию, клиринг, отчёты;
- маршрутизирует транзакции между системами.

### 6.1. Структура процессингового центра (HLD)

| Компонент | Назначение |
|-----------|------------|
| **Front-end** | Приём ISO 8583 сообщений, маршрутизация |
| **Switch** | Определение маршрута (Visa / MC / MIR / локальные) |
| **Authorization Host** | Проверка карт, лимитов, скоринг, антифрод |
| **Clearing Module** | Подготовка и отправка файлов клиринга |
| **Settlement Engine** | Расчёт взаимных обязательств, подготовка проводок |
| **Card Management System (CMS)** | Выпуск карт, статусы, параметры |
| **Fraud Monitoring** | Правила/скоринги/блокировки |
| **Reporting / DWH** | Сводные отчёты, сверки, регуляторные выгрузки |

### 6.2. Пример работы процессинга

1. Клиент оплачивает 500 ₽ картой Visa в магазине.
2. POS → процессинг эквайера → VisaNet → процессинг эмитента.
3. Эмитент проверяет баланс, лимиты, антифрод → возвращает ответ 00.
4. Ответ идёт обратно → чек печатается «Оплата успешна».
5. Процессинг формирует проводку, отчёт и данные для клиринга.

## 7. PCI DSS — стандарт безопасности платёжных данных

**PCI DSS (Payment Card Industry Data Security Standard)** — международный стандарт, определяющий требования к защите карточных данных (PAN, CVV, PIN). Он обязателен для всех организаций, которые хранят, обрабатывают или передают эти данные.

### 7.1. Основные принципы PCI DSS (v4.0)

| Категория | Примеры требований |
|-----------|-------------------|
| **Сеть** | Сегментировать платёжную зону, ограничить доступ |
| **Данные** | Хранить PAN в зашифрованном виде, запрет хранения CVV, PIN |
| **Доступ** | MFA для администраторов, минимальные права |
| **Мониторинг** | Логировать все операции, хранить ≥ 1 года |
| **Тестирование** | Регулярные сканирования и пентесты |
| **Управление сертификатами** | Инвентаризация и контроль жизненного цикла ключей |

### 7.2. Применение для системного аналитика

- В требованиях прописывать **маскирование PAN** (например, `220077******1234`).
- Запрещать логирование CVV, ExpDate, PIN.
- Проверять, что интеграции используют HTTPS/TLS 1.2+ и токенизацию.
- Хранить ссылки на PCI DSS сертификаты контрагентов (процессинг, PSP).
- В ТЗ явно указывать **зоны ответственности**: кто хранит, а кто не хранит данные карт.

## 8. Роль системного аналитика в платёжных технологиях

### 8.1. Задачи на разных этапах

| Этап | Действия аналитика |
|------|-------------------|
| **Исследование** | Изучает правила Visa/MasterCard/МИР, стандарты ISO, требования PCI DSS |
| **Проектирование** | Разрабатывает схемы интеграции: POS → процессинг → ПС → ядро |
| **Форматы данных** | Описывает поля ISO 8583 → JSON → DB |
| **Безопасность** | Контролирует хранение данных, маскирование, токенизацию |
| **Инциденты** | Разбирает ошибки (коды 05, 91, 96 и т.п.) |
| **Мониторинг** | Добавляет метрики в Grafana/ELK (например, `auth_approval_rate`, `stp_rate`) |
| **Тестирование** | Участвует в сертификации платёжных сценариев |
| **Документация** | Ведёт Wiki: маршруты, BIN-таблицы, статусы, SLA |

### 8.2. Примеры конкретных задач

| Ситуация | Что делает аналитик |
|----------|---------------------|
| Новый эквайринг в интернет-магазине | Проектирует интеграцию по ISO 8583 / REST API |
| Проблема с двойным списанием | Проверяет логи процессинга и идемпотентность |
| Запуск 3-D Secure 2.0 | Согласует сценарии и статусы SCA/OTP |
| Клиринг не сошёлся | Анализирует отчёт Visa/MasterCard, проверяет GL-проводки |
| Оптимизация SLA | Разбирает задержки в ISO-сообщениях, топики Kafka |
| Подготовка отчётности | Настраивает выгрузку MT940 / internal ledger |

## 9. Пример аналитического фрагмента FSD (для нашего кейса)

**Функция**: авторизация транзакции по карте МИР на сумму 3 390 ₽.

**Источник**: POS/эквайер → процессинг → НСПК → эмитент.

**События**:
- `mir.auth.request` — запрос авторизации;
- `mir.auth.response` — ответ эмитента;
- `mir.clearing.file.created` — начало клиринга;
- `payment.settled` — финальное зачисление.

**Условия**:
- Лимиты и антифрод проверяются до авторизации.
- Время ответа ≤ 3 сек; при таймауте — ретрай 2 раза, DLQ после 10 сек.
- Маскирование PAN (поля 2, 35, 52).
- События публикуются в Kafka с Avro-схемой v2.

**Статусная модель**:
```
INITIATED → AUTHORIZED → CLEARING → SETTLED
          ↘ REVERSED (если отмена)
          ↘ FAILED (ошибка)
```

**Идемпотентность**: ключом служит комбинация `RRN` (Retrieval Reference Number) + `STAN` (System Trace Audit Number).

## 10. ⭐ Дополнительные разделы для углублённого понимания

### 10.1. Коды ответов ISO 8583 (наиболее частые)

| Код | Расшифровка | Действие аналитика |
|-----|-------------|-------------------|
| 00 | Approved | Успех, можно продолжать |
| 05 | Declined (недостаточно средств или лимит) | Проверить баланс, предложить другую карту |
| 51 | Insufficient funds | Аналогично 05 |
| 91 | Timeout (связь с эмитентом) | Ретрай, проверка таймаутов |
| 96 | System malfunction | Ошибка на стороне эмитента, логирование |
| 30 | Format error | Проверить структуру ISO-сообщения |

### 10.2. 3-D Secure 2.0

**3-D Secure** — протокол аутентификации держателя карты при интернет-платежах. Версия 2.0 использует **SCA** (Strong Customer Authentication) и передаёт дополнительные данные об устройстве, местоположении, истории покупок для снижения числа ложных отказов.

**Для аналитика**:
- Описать точки вызова 3DS (до авторизации).
- Согласовать сценарии: `AUTHENTICATION_SUCCESS`, `CHALLENGE_REQUIRED`, `FAILED`.
- Учесть интеграцию с ACS (Access Control Server) эмитента.

### 10.3. Токенизация

Токенизация — замена PAN на уникальный токен, который можно использовать для платежей без хранения реального номера карты. Это снижает область применения PCI DSS.

**Пример**: при первом платеже клиента мы сохраняем токен, полученный от процессинга, и используем его для повторных оплат.

**Для аналитика**:
- Описать процесс получения и хранения токена.
- Указать, что токен не подлежит обратному преобразованию.

### 10.4. Реконсилиация (сверка)

Реконсилиация — процесс сравнения внутренних данных (проводок, статусов) с внешними отчётами (платёжной системы, эквайера). Расхождения могут быть вызваны задержками, дублями, ошибками форматов.

**Для аналитика**:
- Описать периодичность сверки (ежедневно, еженедельно).
- Определить форматы выгрузок (MT940, файлы клиринга).
- Настроить алерты при расхождениях > 0,01%.

## 11. Чек-лист аналитика при проектировании платёжных интеграций

- [ ] Определены все участники (эмитент, эквайер, процессинг, ПС).
- [ ] Изучены требования платёжной системы (правила, комиссии, сроки).
- [ ] Статусная модель покрывает все этапы (auth → clearing → settlement, а также ошибки и реверсы).
- [ ] Описаны события в Kafka для каждого изменения статуса.
- [ ] Предусмотрена идемпотентность (ключи RRN+STAN или Idempotency-Key).
- [ ] Проработаны таймауты, ретраи, DLQ.
- [ ] Учтены требования PCI DSS (маскирование, запрет логирования, шифрование).
- [ ] Определены точки вызова AML/антифрод.
- [ ] Описаны форматы сообщений (ISO 8583 → JSON, маппинг полей).
- [ ] Согласованы cut-off time и график расчётов (T+1).
- [ ] Предусмотрена реконсилиация и отчётность.
- [ ] Закреплены SLA (например, ответ на авторизацию ≤ 3 сек).

## 12. Заключение

Платёжные технологии — это сложная экосистема с жёсткими регуляторными и техническими требованиями. Ключевые принципы, которые должен усвоить системный аналитик:

1. **Чётко различать авторизацию, клиринг и расчёт** — временные разрывы критичны для бизнес-логики.
2. **Учитывать задержки** при проектировании статусов и уведомлений (например, не переводить заказ в PAID до получения settlement).
3. **Понимать стандарты** (ISO 8583, ISO 20022, PCI DSS) и их влияние на интеграции.
4. **Проектировать идемпотентность, ретраи и наблюдаемость** — это основа надёжности.
5. **Всегда держать в голове регуляторные требования** (AML, KYC, валютный контроль).

## 14. Глоссарий

| Термин | Определение |
|--------|-------------|
| **Эмитент** | Банк, выпустивший карту клиента |
| **Эквайер** | Банк, обслуживающий торговую точку |
| **Процессинг** | Платформа для обработки транзакций (авторизация, клиринг, отчёты) |
| **Платёжная система** | Организация, задающая правила и маршруты (Visa, MC, МИР) |
| **SWIFT** | Сеть для обмена финансовыми сообщениями (международные переводы) |
| **ISO 8583** | Стандарт сообщений для карточных транзакций (авторизация, клиринг) |
| **ISO 20022** | Современный стандарт для платёжных сообщений (межбанк, отчётность) |
| **PCI DSS** | Стандарт безопасности данных платёжных карт |
| **Hold** | Временная блокировка суммы на карте при авторизации |
| **Клиринг** | Этап подтверждения и взаимозачёта транзакций между банками |
| **Settlement** | Финальное списание/зачисление через корреспондентские счета |
| **Reversal** | Отмена авторизации |
| **Chargeback** | Оспаривание платежа клиентом |
| **3-D Secure** | Протокол аутентификации держателя карты в интернете |
| **Токенизация** | Замена PAN на уникальный токен для безопасного хранения |
