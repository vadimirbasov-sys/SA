# Лекция: Банковские переводы, счета, карты, кредиты  
## (на примере оплаты аренды сервера 3 390 ₽)

---

## 1. Введение: контекст и проблема

**Кейс**: клиент Дмитрий Гордеев оплачивает аренду сервера в ЛК хостинг-провайдера. Это классический **C2B-платёж**: деньги движутся от физического лица к расчётному счёту организации. На предыдущих этапах мы рассматривали архитектуру платежа, жизненный цикл транзакции, MDM и DWH. Теперь мы смотрим на этот же процесс **с банковской стороны**: какие счета участвуют, как строится маршрут в АБС, какие статусы проходят переводы и как обеспечивается идемпотентность.

**Боль**: клиент нажал «Оплатить», система зафиксировала статус `INITIATED`, затем `VALIDATED` (лимиты, KYC, баланс OK). Но в этот момент сеть оборвалась, и клиент не получил ответ. Он повторно нажал кнопку (без `Idempotency-Key`) → система создала второй платёж → двойное списание 3 390 ₽. Клиент видит два списания, пишет жалобу, поддержка оформляет возврат, расходы на расследование — часы работы трёх команд.

**Задача аналитика**: описать API, статусную модель, идемпотентность, связь с таблицей `Orders`, а также спроектировать корректную обработку счетов, карт и кредитных инструментов.

## 2. API платежа: пример и статусная модель

### 2.1. POST /api/v1/payments (фрагмент ТЗ)

Принимает JSON:
```json
{
  "payer": {
    "account_id": "acc_44021081099238120001",
    "client_id": "cl_000001"
  },
  "payee": {
    "account_id": "acc_40702810100000001234",
    "bik": "044525225",
    "name": "ООО «Облачный хостинг»"
  },
  "amount": { "value": 3390.00, "currency": "RUB" },
  "purpose": "Оплата заказа №101, аренда сервера",
  "order_ref": "101",
  "channel": "MOBILE_APP"
}
```
- Валидирует лимиты, KYC, AML, баланс.
- Публикует `payment.initiated` в Kafka.
- Возвращает `payment_id`, статус, ссылку на чек.
- Асинхронно: статус обновляется через `GET /payments/{id}` или webhook.

### 2.2. Жизненный цикл платежа

| Статус | Описание |
|--------|----------|
| `INITIATED` | Запрос принят API Gateway, но ещё не обработан. |
| `VALIDATED` | Проверки (лимиты, KYC, AML, баланс) пройдены. |
| `SENT` | Запрос передан в АБС / платёжную систему. |
| `CONFIRMED` | Платёж успешно выполнен (деньги списаны/зачислены). |
| `FAILED` | Ошибка на любом этапе (отказ, таймаут, тех. сбой). |
| `REVERSED` | Отмена после подтверждения (например, по запросу клиента). |

**Важно**: при повторе POST с тем же `Idempotency-Key` сервер возвращает тот же `payment_id` и статус, не создавая новый платёж.

### 2.3. Идемпотентность – практический подход

- Клиент генерирует уникальный ключ (UUID v4) для каждой новой операции.
- Сервер сохраняет ключ и результат первого успешного запроса.
- При повторных вызовах с тем же ключом в течение заданного времени (например, 24 часа) сервер возвращает сохранённый результат, не выполняя операцию заново.

**Пример требования в SRS**:
> При POST `/payments` клиент обязан передавать заголовок `Idempotency-Key`. Повторный вызов с тем же ключом возвращает тот же `payment_id` и статус. Если ключ не передан, сервер должен сгенерировать его автоматически, но тогда идемпотентность не гарантируется для клиента.

## 3. Виды переводов (справочник)

| Тип | Пример | Особенности |
|-----|--------|-------------|
| **Внутренний** | перевод между счетами одного банка | Мгновенно, без посредников. |
| **Межбанковский (через ЦБ)** | перевод с расчётного счёта в банк А на счёт в банк Б | Проходит через систему расчётов ЦБ РФ (платёжная система Банка России). |
| **Международный (SWIFT)** | перевод USD/EUR за границу | Комиссии, валютный контроль, форматы MT103 / ISO 20022. |
| **По номеру телефона (СБП)** | P2P-перевод через Систему быстрых платежей | Мгновенно, лимиты до 1 млн ₽ (с 2025 года). |
| **Бюджетный** | оплата налогов, штрафов | Участвует казначейство, КБК, ОКТМО. |

Аналитик должен для каждого типа перевода описать:
- Маршрут в АБС,
- Необходимые проверки (валютный контроль, AML),
- Статусы и события,
- Возможные задержки и SLA.

## 4. Счета и карты: модели данных

### 4.1. Структура счёта в API и АБС

```json
{
  "account_id": "acc_44021081099238120001",
  "client_id": "cl_000001",
  "iban": "RU44021081099238120000123456789012",
  "balance": {
    "available": 125000.50,
    "blocked": 3390.00,
    "currency": "RUB"
  },
  "status": "ACTIVE",
  "type": "CURRENT",
  "product_code": "RKO_INDIVIDUAL",
  "opened_at": "2022-03-15T10:00:00Z"
}
```

**Важное правило**: баланс — это сумма операций по двойной записи (DR/CR). Все изменения только транзакциями, с соблюдением ACID.

### 4.2. Типы счетов

- Расчётный (для юрлиц и ИП),
- Текущий (для физлиц),
- Карточный (привязан к карте, часто с овердрафтом),
- Кредитный (ссудный счёт),
- Депозитный,
- Брокерский,
- ИИС (индивидуальный инвестиционный счёт).

### 4.3. Карты – интерфейс к счёту

- Дебетовые (средства клиента),
- Кредитные (средства банка, с лимитом),
- Предоплаченные / виртуальные.

**Основные атрибуты**:
- PAN (номер карты),
- ExpDate, CVV,
- BIN (первые 6 цифр – определяют платёжную систему и тип карты),
- Card Product (МИР Classic, Visa Gold, MC World),
- Cardholder name.

### 4.4. Токенизация – безопасность без хранения PAN

**Зачем**: чтобы не хранить настоящие номера карт у мерчанта, снижая область PCI DSS.

**Как работает**:
1. Пользователь добавляет карту в Apple Pay / Google Pay.
2. Данные шифруются и отправляются в процессинг → Visa/MC → токен-провайдер.
3. Возвращается токен (Device Account Number).
4. При оплате используется токен вместо PAN.
5. Процессинг подменяет токен на PAN и отправляет эмитенту.

**Аналитик описывает**:
- API токенизации (создание, обновление, отзыв),
- Статусы токенов: `ISSUED`, `ACTIVATED`, `SUSPENDED`, `REVOKED`,
- События: `token.created`, `token.updated`, `token.deleted`,
- Маскирование токена, хранение `device_id`.

## 5. Дебет и кредит – бухгалтерская суть

В банковской системе каждая операция отражается как минимум двумя проводками: дебет одного счёта и кредит другого. Сумма дебетов равна сумме кредитов.

| Тип | Что значит | Пример |
|-----|------------|--------|
| **Дебет (DR)** | Увеличение активов (для банка) или списание (для клиента) | Списание 3 390 ₽ со счёта клиента |
| **Кредит (CR)** | Увеличение обязательств (для банка) или зачисление (для клиента) | Зачисление 3 390 ₽ на корсчёт банка |

**Пример проводки** (для оплаты аренды):
- Дебет счёта клиента (уменьшение) – 3 390 ₽.
- Кредит корсчёта банка (увеличение) – 3 390 ₽.

**Для аналитика** важно:
- В требованиях указывать, какие GL-коды (счета главной книги) участвуют.
- Проверять, что для каждого платежа формируются проводки сбалансированно.
- Учитывать, что при возврате или чарджбеке выполняются обратные проводки.

## 6. Мерчанты и их подключение

**Мерчант** – бизнес, принимающий оплату картами или переводами.

| Элемент | Описание |
|---------|----------|
| **Merchant ID (MID)** | Уникальный идентификатор торговца в платёжной системе. |
| **Терминалы (TID)** | Устройства (POS-терминалы, виртуальные терминалы), привязанные к MID. |
| **MCC** (Merchant Category Code) | Категория бизнеса (5411 – супермаркеты, 7999 – фитнес). |
| **Settlement Account** | Счёт для зачисления средств от эквайера. |
| **Комиссии / тарифы** | % от суммы операции (зависит от MCC, типа карты). |
| **Chargeback rules** | Процедуры оспаривания транзакций. |
| **Проверки AML / KYC** | Верификация компании перед подключением. |

Аналитик описывает:
- Модель данных мерчанта в CRM / АБС,
- Интеграцию с антифрод-модулем (маршрутизация по MCC),
- Правила расчёта комиссий и отображения в отчётах.

## 7. Кредитный скоринг

Кредитный скоринг – оценка вероятности возврата кредита на основе данных о клиенте.

### 7.1. Этапы скоринга

1. **Заявка** – клиент заполняет анкету (ФИО, доход, работа, цель кредита).
2. **Обогащение** – запросы в БКИ, ФНС, ПФР, мобильные операторы, антифрод.
3. **Скоринг-модель** – машинное обучение / логистическая регрессия → балл риска.
4. **Решение** – если `Score >= Threshold` → одобрение, иначе отказ или ручная проверка.

### 7.2. Пример бизнес-правил

| Правило | Проверка | Действие |
|---------|----------|----------|
| Возраст < 21 года | отказ | `REJECT_REASON = TOO_YOUNG` |
| Доход < 20 000 ₽ | отказ | `REJECT_REASON = LOW_INCOME` |
| Просрочка > 30 дней в БКИ | ручная проверка | `STATUS = REVIEW` |
| Score ≥ 720 | одобрение | лимит до 300 000 ₽ |

### 7.3. Метрики скоринга

| Метрика | Что означает | Цель |
|---------|--------------|------|
| **Approval Rate** | Доля одобренных заявок | 60–70 % |
| **Default Rate** | Просрочка > 90 дней | < 5 % |
| **Bad Rate** | Плохие клиенты / одобренные | ≤ 3 % |
| **TAT** (Time-to-Approve) | Время принятия решения | ≤ 30 сек |

**Хороший скоринг – это баланс.** Слишком жёсткие правила → низкий Approval Rate → теряем клиентов. Слишком мягкие → высокий Default Rate → теряем деньги.

## 8. Индивидуальный инвестиционный счёт (ИИС)

ИИС – специальный брокерский счёт для физических лиц, дающий налоговые льготы.

| Тип ИИС | Что даёт |
|---------|----------|
| **Тип А** | Налоговый вычет на взносы (до 400 000 ₽/год) – возврат 13% НДФЛ. |
| **Тип Б** | Освобождение от налога на прибыль от инвестиций (без вычета). |

**Как работает**:
1. Клиент открывает ИИС у брокера (в банке).
2. Вносит деньги (только от своего имени).
3. Инвестирует в акции, облигации, ПИФы.
4. При закрытии счёта или через 3 года получает льготу.

**Аналитик описывает**:
- Процессы открытия, взноса, покупки/продажи ценных бумаг.
- Интеграцию с налоговой (API вычетов).
- Отчётность для клиента (оборотка, НДФЛ).
- Контроль: «1 клиент = 1 ИИС».

## 9. 🔥 Дополнительные разделы (расширение)

### 9.1. Корреспондентские счета (Loro / Nostro)

При межбанковских расчётах используются корреспондентские счета:
- **Nostro** – счёт нашего банка в банке-контрагенте (актив).
- **Loro** – счёт банка-контрагента в нашем банке (пассив).

**Для аналитика**:
- В требованиях указывать, через какой корсчёт идёт расчёт (BIC, SWIFT-код).
- Учитывать задержки и ликвидность корсчетов.
- Описывать реконсилиацию по остаткам.

### 9.2. Обработка возвратов и чарджбеков

- **Refund** – добровольный возврат средств мерчантом клиенту. Создаётся обратная транзакция с тем же RRN, списывается с мерчанта, зачисляется клиенту.
- **Chargeback** – принудительный возврат по инициативе банка (оспаривание). Может быть вызван мошенничеством, технической ошибкой или недовольством клиента.

**Аналитик должен описать**:
- Статусы: `REFUND_INITIATED`, `REFUND_COMPLETED`, `CHARGEBACK_OPEN`, `CHARGEBACK_RESOLVED`.
- События в Kafka для уведомления систем (Order, CRM).
- Правила сроков (например, chargeback возможен в течение 120 дней).
- Влияние на GL-проводки (обратные проводки).

### 9.3. Аннуитетные и дифференцированные кредитные платежи

Для кредитных продуктов важно различать схемы погашения:

| Схема | Особенность | Расчёт |
|-------|-------------|--------|
| **Аннуитет** | Равные ежемесячные платежи, в начале больше процентов, в конце – тело. | Платёж = (Сумма * ставка) / (1 - (1+ставка)^(-срок)) |
| **Дифференцированный** | Тело кредита погашается равными долями, проценты на остаток. | Платёж = тело/срок + остаток*ставка/12 |

Аналитик описывает:
- API расчёта графика платежей,
- Модель данных графика,
- События при наступлении даты платежа,
- Расчёт штрафов и пеней при просрочке.

### 9.4. Лимиты и комиссии – как проектировать

Лимиты могут быть:
- По сумме операции (суточные, месячные).
- По количеству операций.
- По категории (MCC, тип получателя).
- По каналу (мобильный банк, интернет-банк, отделение).

Комиссии могут быть:
- Фиксированные (например, 50 ₽).
- Процентные (например, 1% от суммы).
- Смешанные (min + %).

**Для аналитика**:
- Создать справочник лимитов и комиссий, привязанный к продуктам и тарифам.
- Описать логику проверки лимитов перед списанием.
- Предусмотреть исключения (VIP-клиенты, специальные акции).

## 10. Типовые ошибки и подводные камни (как в предыдущих лекциях)

1. **Двойное списание** – отсутствие идемпотентности.
2. **Расхождения сумм** – из-за комиссий, курсов, неправильных округлений.
3. **Некорректные статусы** – например, перевод в `CONFIRMED` до фактического settlement.
4. **Задержки в DWH** – использование DWH для оперативного статуса заказа.
5. **Отсутствие обратных проводок** – при возвратах нарушается баланс GL.
6. **Неправильные GL-коды** – ошибки в бухгалтерских справочниках.
7. **Неучёт валютных курсов** – при мультивалютных переводах.
8. **Игнорирование cut-off time** – переводы после клирингового окна сдвигаются на следующий день.

## 11. Чек-лист аналитика при проектировании переводов и счетов

- [ ] Описана статусная модель (INITIATED → VALIDATED → SENT → CONFIRMED / FAILED / REVERSED).
- [ ] Внедрена идемпотентность через Idempotency-Key (или комбинацию RRN+STAN).
- [ ] Определены все типы счетов и их атрибуты.
- [ ] Учтены требования к токенизации и PCI DSS.
- [ ] Описаны GL-коды и двойная запись для каждой операции.
- [ ] Заданы лимиты и комиссии (справочники, правила применения).
- [ ] Определены точки вызова AML / антифрод.
- [ ] Описаны события в Kafka для каждого изменения статуса.
- [ ] Учтены задержки межбанковских расчётов (T+1 и т.д.).
- [ ] Предусмотрена обработка возвратов и чарджбеков.
- [ ] Для кредитных продуктов описан график платежей и схема начисления процентов.
- [ ] В требованиях указаны SLA (например, ответ на запрос ≤ 3 сек, settlement ≤ T+1).
- [ ] Подготовлены метрики для мониторинга (approval_rate, stp_rate, decline_reasons).

## 13. Заключение

В этой лекции мы рассмотрели банковскую сторону платежей: как проектируются переводы, счета, карты, кредиты и скоринг. Главные выводы:
- **Идемпотентность** – критически важна, чтобы избежать двойных списаний.
- **Двойная запись** – основа бухгалтерской корректности.
- **Счета и карты** – это не просто сущности, а контракты с Core Banking.
- **Токенизация** – обязательный элемент современных платёжных систем.
- **Кредитный скоринг** – требует баланса между риском и доступностью.
- **Возвраты и чарджбеки** – нужно проектировать с самого начала.
- **Лимиты и комиссии** – должны быть гибкими и управляемыми через справочники.

## 15. Глоссарий

| Термин | Определение |
|--------|-------------|
| **Идемпотентность** | Свойство операции, при котором повторный вызов с теми же параметрами даёт тот же результат. |
| **Двойная запись** | Принцип бухгалтерии: каждая операция отражается на двух счетах (дебет и кредит). |
| **Токенизация** | Замена PAN на безопасный токен для платежей. |
| **PAN** | Первичный номер карты (Primary Account Number). |
| **MCC** | Код категории мерчанта (Merchant Category Code). |
| **MID** | Идентификатор торговой точки в платёжной системе. |
| **GL (General Ledger)** | Главная книга – центральный учёт всех проводок. |
| **RRN (Retrieval Reference Number)** | Уникальный номер для поиска транзакции в системе. |
| **STAN (System Trace Audit Number)** | Порядковый номер транзакции в терминале. |
| **Chargeback** | Оспаривание платежа держателем карты. |
| **Refund** | Добровольный возврат средств мерчантом. |
| **Settlement** | Финальный расчёт между банками через корреспондентские счета. |
| **ИИС** | Индивидуальный инвестиционный счёт (налоговые льготы). |
| **БКИ** | Бюро кредитных историй (хранит кредитную историю). |
