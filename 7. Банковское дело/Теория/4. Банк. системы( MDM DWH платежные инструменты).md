# Лекция: Банковские системы: MDM, DWH, платежные инструменты  
## (на примере клиента Дмитрия Гордеева и заказа №101)

---

## 1. Введение: контекст и проблема

**Кейс**: клиент Дмитрий Гордеев оформляет заказ на аренду сервера (№101) в личном кабинете CRM. В мобильном банке он отображается как «Д. Гордеев», а в хранилище данных (DWH) появляются три разные строки. Когда бизнес пытается построить отчёт «выручка по аренде» — цифры не сходятся. Проблема не в плохом SQL, а в **отсутствии единой системы управления мастер-данными (MDM)**.

**Боль**:
- В CRM клиент имеет ID = `cl_000001` и имя «Дмитрий Гордеев».
- В Core Banking (АБС) тот же клиент имеет номер счёта `acc_44021081099238120001` и имя «Д. Гордеев».
- В Marketing DWH он фигурирует как `user_8842` с email `d.gord@…`.

Платёж на 3 390 ₽ привязан к счёту в АБС, а заказ — к `ClientID=1`. Без **золотой записи** (единого идентификатора) аналитик не сможет склеить данные и понять, что это один и тот же человек, что приводит к ошибкам в отчётности, аналитике повторных продаж и клиентских сегментах.

**Цель лекции**:
- Понять, что такое MDM и зачем он нужен в банке.
- Изучить архитектуру DWH и его роль в аналитике.
- Разобраться в платежных инструментах (банкоматы, NFC, токенизация) и их интеграции.
- Узнать, как системный аналитик описывает данные, идентификаторы и требования к консистентности.

## 2. MDM (Master Data Management) – единый источник истины

### 2.1. Зачем нужен MDM в банке
- Обеспечивает все системы банка (CRM, АБС, процессинг, DWH) едиными идентификаторами и справочниками.
- Исключает дубли: «Иванов И.И.» и «Иванов Иван Иванович» — один человек.
- Гарантирует качество и консистентность данных для всех downstream-систем.

### 2.2. Как работает MDM
1. **Приём данных** – из разных источников (CRM, Core Banking, карточная система) поступают сведения о клиентах, договорах, счетах.
2. **Очистка и нормализация** – данные очищаются от опечаток, приводятся к единым форматам (ФИО, даты, номера телефонов).
3. **Дедупликация (matching)** – применяются правила сопоставления (например, ФИО + ИНН + дата рождения + телефон) с расчётом **порога уверенности** (confidence score).
   - Если порог достигнут – записи автоматически объединяются в **золотую запись**.
   - Если порог не достигнут – запись отправляется на ручной разбор (stewardship).
4. **Присвоение глобального идентификатора (GUID)** – каждой золотой записи присваивается уникальный идентификатор, который становится единым ключом для всех систем.
5. **Рассылка (публикация)** – обновлённые записи с GUID отправляются обратно в системы-подписчики через REST API или Kafka.

### 2.3. Архитектура MDM (схема)

```
Источники данных:
CRM (cl_000001)  →  │
Core Banking      →  │
(acc_...001)     →  │
Card System       →  │
(user_8842)      →  │
                    ▼
              ┌───────────┐
              │  MDM Hub  │
              │ (Приём)   │
              └───────────┘
                    │
                    ▼
              ┌───────────┐
              │ Data      │
              │ Quality   │
              │ (очистка) │
              └───────────┘
                    │
                    ▼
              ┌───────────┐
              │ Matching  │
              │ (дедупл.) │
              │ Правила:  │
              │ ФИО+ИНН+  │
              │ тел+дата  │
              └───────────┘
                    │
                    ▼
              ┌───────────┐
              │ Golden    │
              │ Record    │
              │ GUID =    │
              │ mdm_001   │
              └───────────┘
                    │
                    ▼
         ┌─────────────────────┐
         │ Публикация подписчикам│
         │ CRM, DWH, Marketing  │
         └─────────────────────┘
```

### 2.4. Что делает системный аналитик в MDM-проекте

| Этап | Действия аналитика |
|------|-------------------|
| **Анализ** | Определяет все источники данных (CRM, АБС, процессинг, контактные центры). |
| **Моделирование** | Проектирует сущности: `Person`, `Organization`, `Account`, `Contract`, `Product`. |
| **Настройка правил** | Задаёт алгоритмы matching/merging: какие поля сравнивать, какие веса, какой порог уверенности. |
| **Интеграция** | Описывает API и события (REST, Kafka) для приёма и публикации данных, форматы (JSON, Avro). |
| **Документация** | Создаёт описание жизненного цикла записи: статусы (`NEW`, `MATCHED`, `GOLDEN`, `STEWARD`), ошибки. |
| **Качество** | Добавляет метрики: `duplicate rate`, `completeness`, `steward workload`. |

### 2.5. Преимущества MDM

| Преимущество | Для чего |
|--------------|----------|
| **Единые клиентские данные** | Исключение дублей, точное количество клиентов. |
| **Быстрая аналитика** | Консистентные данные для отчётности без ручных сверок. |
| **Упрощённая интеграция** | Единый GUID во всех системах, снижение затрат на маппинг. |
| **Ускорение KYC/AML** | Меньше ошибок в проверках, правильные санкционные списки. |
| **Меньше ручных операций** | Автоматическая синхронизация данных. |

### 2.6. Ключевой момент для нашего кейса
Без MDM аналитик не сможет склеить «заказ → оплата → повторная аренда» – три разных ID = три разных клиента. Именно на этапе дедупликации MDM объединяет «Дмитрий Гордеев» из CRM, «Д. Гордеев» из Core Banking и `d.gord@...` из Marketing DWH в единую золотую запись с GUID `mdm_001`.

## 3. DWH (Data Warehouse) – хранилище для аналитики

### 3.1. Зачем нужен DWH
DWH собирает данные из всех операционных систем банка (Core, CRM, MDM, процессинг) и преобразует их в форму, удобную для аналитики, отчётности, BI и машинного обучения.

### 3.2. Архитектура DWH (слои)

| Слой | Описание |
|------|----------|
| **Stage** | Необработанные данные, выгруженные из источников (сырые копии таблиц). |
| **ODS (Operational Data Store)** | Операционные данные, очищенные и приведённые к единым форматам, но ещё не агрегированные. |
| **Core / EDW** | Центральная модель данных (звёздная схема, нормализованная или размерная). Здесь хранятся факты и измерения. |
| **Data Marts** | Отчётные витрины для конкретных бизнес-задач (например, витрина по доходам от аренды, витрина по клиентской активности). |

### 3.3. ETL / ELT процесс
- **Extract** – выгрузка данных из источников (CDC, полные выгрузки, файлы).
- **Transform** – очистка, нормализация, объединение с MDM GUID, агрегация, расчёт показателей.
- **Load** – загрузка в целевые таблицы DWH.

Современные подходы используют **ELT** – сначала загрузка, потом трансформация внутри DWH (например, с помощью dbt).

### 3.4. Звёздная схема (факты и измерения)
Для отчётов обычно используется **звёздная схема**:
- **Факты** – числовые показатели (суммы платежей, количество заказов).
- **Измерения** – справочники (клиенты, время, продукты, каналы).

**Пример** для нашего кейса:
- Факт: `payment_fact` (сумма, дата, статус).
- Измерения: `dim_client` (GUID из MDM), `dim_order`, `dim_date`.

### 3.5. Задержка DWH (ETL latency)
DWH не содержит «живых» данных – обновление происходит по расписанию (ежечасно, ежедневно). Поэтому статус заказа (например, `PAID`) нужно смотреть в операционной системе (АБС), а не в DWH, если важна актуальность в реальном времени.

### 3.6. Метрики и SLA для DWH

| Метрика | Значение (типичное) |
|---------|---------------------|
| ETL latency | ≤ 1 часа от момента транзакции |
| Data accuracy | ≥ 99.9 % |
| Availability | 24/7 |
| Retention | 3–5 лет для транзакций |
| Data freshness | обновление по расписанию (ежечасно / ежедневно) |

### 3.7. Задачи системного аналитика в DWH-проекте

| Задача | Описание |
|--------|----------|
| **Описать источники и lineage** | Показать путь данных: от источника до витрины. |
| **Согласовать поля** | Утвердить, какие поля и в каком формате поступают в DWH (например, `account_id`, `transaction_id`, `amount`, `timestamp`). |
| **Проверить связность** | Убедиться, что в DWH присутствует MDM GUID для склейки данных. |
| **Задать SLA** | Определить время загрузки, алерты при задержках. |
| **Подготовить регламентные отчёты** | Для регуляторов и внутреннего бизнеса. |

## 4. Взаимосвязь MDM и DWH

MDM и DWH работают в тесной связке:
1. **MDM** создаёт и поддерживает **золотую запись** клиента с GUID.
2. **DWH** использует этот GUID как **внешний ключ** для объединения данных из разных источников в аналитических отчётах.
3. Без MDM в DWH будут дубли и несогласованность – отчёты станут бесполезны.

**Пример**: отчёт «количество клиентов, сделавших повторный заказ» требует точного определения клиента. MDM даёт единый идентификатор, и DWH по нему группирует заказы.

## 5. Платежные инструменты и каналы

### 5.1. Банкомат (ATM)

**Архитектура**:
Банкомат → процессинг → АБС → ядро банка.

**Как работает**:
1. Клиент вставляет карту → считываются данные (PAN, магнитная дорожка).
2. Банкомат запрашивает PIN → проверка в HSM (шифрованная зона).
3. Отправляется ISO 8583 запрос на авторизацию (поля: сумма, PAN, терминал, STAN, RRN).
4. Процессинг маршрутизирует запрос к эмитенту.
5. Эмитент проверяет баланс, лимиты, антифрод → возвращает код ответа.
6. Банкомат выдает наличные (или отказывает), печатает чек, записывает событие в журнал.

**События для аналитика**:
- `atm.auth.request`
- `atm.auth.response`
- `atm.cash.dispensed`
- `atm.audit.completed`

**Что описывает аналитик**:
- Статусы: `SUCCESS`, `DECLINED`, `TIMEOUT`, `TECHNICAL_ERROR`.
- Форматы ISO-полей в запросах/ответах.
- SLA: ответ ≤ 10 секунд.
- Аудит и инкассация (журналы, сверки).

### 5.2. Платежные платформы: Apple Pay, Google Pay, SberPay

**Принцип работы (токенизация)**:
1. Клиент добавляет карту в приложение → банк-эмитент генерирует **токен** (Device Account Number) вместо реального PAN.
2. Токен хранится в защищённом элементе устройства.
3. При оплате через NFC терминалу передаётся токен и криптограмма (динамический код).
4. Процессинг получает токен, подменяет его на реальный PAN (по данным токенизационной платформы) и отправляет запрос эмитенту.
5. Эмитент авторизует операцию и возвращает ответ.

**Что описывает аналитик**:
- API токенизации (запрос на создание токена, обновление, отзыв).
- События: `token.created`, `token.updated`, `payment.authorized`.
- Статусы токенов: `ACTIVE`, `SUSPENDED`, `REVOKED`.
- Коды ошибок (например, 91 — недоступен эмитент).

### 5.3. NFC и MST

| Технология | Как работает | Где применяется |
|------------|--------------|-----------------|
| **NFC** | Передача данных при близком контакте (<4 см), шифрованный канал | Apple Pay, Google Pay, бесконтактные карты (PayPass, PayWave) |
| **MST** | Эмуляция магнитной полосы – передаёт данные на старые терминалы (устаревает) | Samsung Pay |

Для аналитика важно знать, что **MST уходит в прошлое**, а **NFC** — основной стандарт. В требованиях нужно описывать только NFC и токенизацию, соответствуя PCI DSS.

## 6. Практические рекомендации для системного аналитика

### 6.1. Требования к идентификаторам
- В каждом API и событии обязательно указывать **MDM GUID** клиента, если он известен.
- В операционных системах (CRM, АБС) должен быть внешний ключ на MDM GUID (или возможность его получить через справочник).

### 6.2. Задержки и актуальность
- Статус заказа (`CREATED`, `PAID`, `SHIPPED`) – читать из **OLTP-систем** (CRM, АБС), а не из DWH, потому что DWH имеет задержку.
- Для аналитических отчётов использовать DWH, но с указанием временного лага.

### 6.3. Безопасность и PCI DSS
- Токенизация снижает область применения PCI DSS, но требует соответствия стандартам.
- В логах запрещено хранить PAN, CVV, PIN; нужно маскирование (например, `220077******1234`).

### 6.4. Инструменты
Аналитик не обязан программировать ETL, но должен понимать, какие инструменты используются:

| Область | Инструменты |
|---------|-------------|
| **MDM** | Informatica, IBM InfoSphere, Talend, Oracle MDM, PostgreSQL + Python |
| **ETL** | Airflow, Talend, Pentaho, dbt, DataStage |
| **DWH** | Teradata, Snowflake, Greenplum, ClickHouse, PostgreSQL |
| **BI** | PowerBI, Tableau, Grafana, Superset |
| **Data Quality** | Great Expectations, Soda Core |
| **Мониторинг** | ELK (Elasticsearch + Kibana), Prometheus |

## 8. Дополнительные разделы (для углубления)

### 8.1. Data Lake vs DWH
- **Data Lake** хранит сырые данные в любом формате (структурированные, полуструктурированные, неструктурированные). Подходит для исследования и ML.
- **DWH** содержит структурированные, очищенные и агрегированные данные для бизнес-отчётности.
- В банках часто используют оба подхода: озеро для «песочницы», хранилище для регламентной отчётности.

### 8.2. Stewardship (ручное управление)
Когда автоматическое сопоставление не достигает порога уверенности, запись попадает в очередь на ручную проверку **Data Steward** (специалист по данным). Аналитик должен описать этот процесс, интерфейсы и статусы.

### 8.3. Согласование данных с регулятором
Для отчётов в ЦБ требуется безупречная точность. Здесь роль MDM критична – ошибка в идентификации клиента может привести к штрафам.

## 9. Заключение

В банковской экосистеме данные разрознены по множеству систем (CRM, Core Banking, процессинг, контакт-центры). **MDM** даёт единый идентификатор клиента (золотую запись), а **DWH** собирает фактические данные для аналитики. Без этих компонентов невозможно построить достоверные отчёты, персонализированные предложения и соблюсти регуляторные требования.

Для системного аналитика важно:
- проектировать идентификаторы и справочники,
- описывать потоки данных,
- учитывать задержки,
- обеспечивать безопасность.

## 11. Глоссарий

| Термин | Определение |
|--------|-------------|
| **MDM** | Master Data Management – управление мастер-данными (клиенты, продукты, контрагенты) |
| **Golden Record** | Единственная, согласованная запись о сущности, полученная после дедупликации |
| **GUID** | Глобально уникальный идентификатор, присваиваемый золотой записи |
| **Stewardship** | Ручной разбор записей, не прошедших автоматическое сопоставление |
| **DWH** | Data Warehouse – хранилище данных для аналитики и отчётности |
| **ETL/ELT** | Extract, Transform, Load – процесс загрузки данных |
| **Data Mart** | Витрина данных – подмножество DWH для конкретной задачи |
| **Data Lineage** | Прослеживание происхождения данных от источника до конечного отчёта |
| **Токенизация** | Замена PAN на уникальный токен для безопасного хранения и передачи |
| **NFC** | Near Field Communication – технология бесконтактной передачи данных |
| **HCE** | Host Card Emulation – эмуляция карты в облаке (используется в Android Pay) |
