# Лекция: Информационная безопасность, DDoS, антифрод  
## (на примере оплаты аренды сервера 3 390 ₽)

---

## 1. Введение: контекст и цена ошибки

**Реальный инцидент**: разработчик отлаживал шлюз оплаты для аренды серверов и включил полное логирование:

```python
logger.info(f"Processing payment request: {request.json}")
```

**Последствия**:
- В Elasticsearch в открытом виде оказались PAN, CVV, сроки карт.
- Kibana без должной авторизации была просканирована ботами → **утечка данных**.
- Штрафы от платёжных систем, отзыв сертификата PCI DSS, остановка приёма платежей.

**Как должно быть в ТЗ** (паттерн маскирования):
> Лог-агенты маскируют `card_number` до `4111********1111`. Поле `cvv` не логируется. Тело `POST /v1/payments` в prod-логах — только `payment_id`, `order_ref`, `amount`, `status`.

**Где мы в кейсе**:
ЛК аренды серверов принимает карты. Требования информационной безопасности (ИБ) из этой лекции — обязательный раздел **NFR** (Non-Functional Requirements) к API и платежам. Банки — одна из самых атакуемых отраслей. Ошибки в требованиях часто становятся причиной утечек. Системный аналитик **закладывает защиту до релиза**, а не после пентеста.

## 2. Основы ИБ в банковской сфере

### 2.1. Почему банки — цель №1
- Деньги и персональные данные (ПДн) в больших объёмах.
- Высокая стоимость компрометации (штрафы, репутационные потери).
- Большое количество внешних интеграций (платёжные системы, партнёры, клиенты).

### 2.2. Регуляторные требования
- **PCI DSS** – для карточных данных.
- **ФЗ-152** – для персональных данных (в России).
- **GDPR** – для данных резидентов ЕС.
- **ЦБ РФ** – нормативные акты по кибербезопасности, отчётность об инцидентах.

**Для аналитика**: все эти требования превращаются в конкретные нефункциональные требования к системе.

## 3. Способы защиты от кибератак

Аналитик фиксирует следующие меры в разделе **Security requirements** SRS (или в NFR).

| Метод | Что делает | Как применяется в проекте |
|-------|------------|---------------------------|
| **Сегментация сети** | Разделяет сеть на изолированные зоны (DMZ, внутренняя, PCI-зона) | Внешние сервисы не имеют прямого доступа к ядру (АБС, БД) |
| **Многоуровневая аутентификация (MFA)** | Требует OTP / Push / App подтверждение | При входе в ЛК и для критических операций (например, оплата > 10 000 ₽) |
| **Шифрование** | Защищает данные в передаче и хранении | TLS 1.3 для передачи, AES-256 для хранения |
| **WAF / IDS / IPS** | Фильтруют и блокируют подозрительные запросы | Устанавливаются перед API Gateway и веб-приложениями |
| **Журналирование и аудит** | Фиксирует все действия пользователей | Хранение ≥ 1 года, защищено от изменений |
| **Политика ролей (RBAC)** | Разделяет доступы по ролям и контекстам | Клиент, сотрудник, интеграция – разные права |
| **Патч-менеджмент** | Устранение уязвимостей | Обновления ОС и ПО по расписанию |
| **Секрет-менеджмент** | Безопасное хранение токенов и паролей | HashiCorp Vault, AWS Secrets Manager |
| **Обучение персонала** | Профилактика фишинга и утечек | Ежегодное обучение по ИБ |

**Пример требования**:
> Все API должны поддерживать аутентификацию по OAuth 2.0, передача данных — только через HTTPS (TLS ≥ 1.2). Доступ к административным функциям ограничен ролями (`ROLE_ADMIN`). Логи аутентификации хранятся 1 год, недоступны для модификации.

## 4. Пентестинг (penetration testing)

**Пентест** — это контролируемая «атака» на систему, чтобы выявить уязвимости до того, как это сделают злоумышленники.

### 4.1. Этапы пентеста
1. **Рекогносцировка** – сбор информации (домен, IP, API, версии, уязвимости).
2. **Сканирование** – проверка открытых портов, сервисов, конфигураций.
3. **Эксплуатация (exploit)** – попытка взлома (SQL-инъекции, XSS, обход аутентификации).
4. **Повышение привилегий** – проверка уязвимостей прав.
5. **Отчёт и рекомендации** – документ с найденными проблемами и предложениями.

### 4.2. Пример отчёта пентеста (для аналитика)

| Уязвимость | Критичность | Описание | Рекомендации |
|------------|-------------|----------|--------------|
| SQL-инъекция в `GET /payments` | High | Некорректная фильтрация параметра `order_id` | Добавить prepared statements |
| Утечка заголовка `Server: nginx/1.18.0` | Medium | Раскрытие версии | Скрыть системные заголовки |
| Отсутствие ограничений по паролю | High | Слабая политика паролей | Длина ≥ 10, спецсимволы, блокировка после 5 ошибок |

**Аналитик** изучает отчёт, вносит задачи в backlog на усиление защиты, добавляет новые требования (например, «блокировка после N неудачных логинов»).

## 5. Работа со службой безопасности (СБ)

**СБ** — подразделение банка, отвечающее за киберзащиту, мониторинг, расследования и контроль доступа.

### 5.1. Основные функции СБ
- **ИБ и SOC** – мониторинг атак, DDoS, вредоносов.
- **Фрод-мониторинг** – контроль подозрительных операций.
- **Физическая безопасность** – доступ в помещения, серверные.
- **Инцидент-менеджмент** – расследует утечки, внутренние нарушения.
- **Проверка сотрудников** – контроль доступа, политика увольнений.
- **Верификация поставщиков** – аудит сторонних интеграций.

### 5.2. Взаимодействие аналитика с СБ
- Согласование интеграций (что можно / нельзя логировать, где хранить ПДн).
- Уточнение требований к шифрованию, токенизации, маскированию.
- Получение чек-листа ИБ для API и документации.
- Проведение **Security Review** перед релизом.
- Фиксация требований в разделе «Безопасность» ТЗ / BRD.

## 6. Защита клиентских данных

В банке данные делятся по уровням чувствительности:

| Уровень | Примеры | Требования к защите |
|---------|---------|---------------------|
| **Персональные (ПДн)** | ФИО, дата рождения, паспорт, телефон, e-mail | Хранение по ФЗ-152, маскирование, шифрование |
| **Чувствительные (Sensitive)** | PAN, CVV, PIN, биометрия, 2FA-токены | PCI DSS, шифрование AES-256, токенизация |
| **Коммерческие (Confidential)** | Доходы, кредитная история, тарифы, KPI | Доступ по ролям, NDA, журналирование |

### 6.1. Примеры требований (в ТЗ – раздел Data Protection)
- PAN маскируется (`220077******1234`), CVV не хранится и не логируется.
- ПДн в API передаются только по TLS 1.3, в БД – шифрование at rest.
- Доступ по RBAC (`ROLE_DATA_VIEWER`).
- Удаление ПДн по запросу клиента – ≤ 30 дней.
- Логи API – без ФИО, паспортов, полного тела платежа.

## 7. DDoS (Distributed Denial of Service)

**Кейс**: DDoS на API оплаты аренды – 1 млн req/s вместо 100. Легитимный `POST /v1/payments` не проходит, клиенты жмут «Оплатить» снова → очередь идемпотентных ключей.

### 7.1. Что такое DDoS
Перегрузка запросами с целью сделать сервис недоступным.

### 7.2. Меры защиты

| Мера | Суть |
|------|------|
| **CDN и балансировщики** | Распределяют нагрузку (Cloudflare, Nginx LB) |
| **Rate limiting** | Ограничивают частоту запросов (например, 10 rps на IP) |
| **Web Application Firewall (WAF)** | Фильтрует вредоносные запросы |
| **Geo-фильтрация** | Блокирует подозрительные регионы |
| **Кэширование** | Снижает нагрузку при повторных запросах |
| **Мониторинг и алерты** | Zabbix, Prometheus, Grafana |
| **Failover / DR** | Резервные площадки и кластеры |

### 7.3. Требования аналитика (SLA)
Система выдерживает ≥ 1000 rps (задается в NFR).  
Авто-масштабирование при росте нагрузки.  
Наличие failover-кластера.

## 8. Антифрод-система (Anti-Fraud)

**Антифрод** — система, которая отслеживает подозрительные операции и блокирует мошеннические действия в режиме реального времени.

### 8.1. Принцип работы
1. Клиент совершает операцию (например, перевод 50 000 ₽).
2. Событие попадает в Kafka → антифрод-модуль.
3. Правила / ML-модель оценивают риск.
4. Если риск высокий – транзакция ставится в `REVIEW` или `BLOCKED`.
5. Сотрудник СБ проверяет вручную.

### 8.2. Типы проверок

| Категория | Пример |
|-----------|--------|
| **Поведенческий анализ** | Необычная сумма, время, устройство |
| **Гео-анализ** | Вход из новой страны или IP |
| **Социальный фрод** | Клиент переводит «родственнику» по телефону |
| **Ботовые атаки** | Массовые логины с одних IP |
| **Технический фрод** | Подмена номера, эмуляция устройства |
| **Внутренний фрод** | Действия сотрудников (анализ ролей и логов) |

### 8.3. Метрики антифрода

| Метрика | Что показывает | Цель |
|---------|----------------|------|
| **Fraud detection rate** | Доля найденных мошеннических операций | ≥ 95 % |
| **False Positive rate** | Доля ошибочных блокировок | ≤ 2 % |
| **Avg. Decision Time** | Среднее время принятия решения | ≤ 2 сек |
| **Throughput** | Обрабатываемых событий/сек | ≥ 1000 |

### 8.4. Роль системного аналитика
- Постановка задач: описывает события для антифрода (`transaction.created`).
- Интеграции: проектирует API / Kafka схемы (Avro/JSON).
- Бизнес-правила: фиксирует сценарии в FSD.
- Мониторинг: описывает статусы `OK`, `REVIEW`, `BLOCKED`.
- Метрики: задаёт SLA по скорости и ложным срабатываниям.
- Тестирование: помогает формировать тестовые кейсы (позитив/негатив).

## 9. Дополнительные разделы (расширение)

### 9.1. Безопасность API (OAuth, JWT, API Keys)
- Использовать OAuth 2.0 / OpenID Connect для аутентификации.
- JWT токены с коротким временем жизни (например, 15 минут).
- API Keys для машинных клиентов (интеграций).
- Защита от повторного воспроизведения (nonce, timestamp).

**Пример требования**:
> Все публичные API должны использовать Bearer-токены (JWT) с проверкой подписи. Для служебных интеграций – API Key в заголовке `X-API-Key`. Токены передаются только по HTTPS.

### 9.2. Шифрование данных в покое и передаче
- **В передаче** – TLS 1.3, строгий набор шифров, сертификаты от доверенного CA.
- **В покое** – шифрование на уровне диска (LUKS, BitLocker) или на уровне БД (TDE).
- **Ключи шифрования** – хранить в HSM или секрет-менеджере (Vault), ротация по расписанию.

### 9.3. Мониторинг и SIEM
- Централизованный сбор логов (ELK, Splunk).
- SIEM-система для корреляции событий и обнаружения атак.
- Настройка алертов: неудачные логины, подозрительные запросы, изменения конфигурации.
- Аналитик описывает требования к журналированию: какие события, какие поля, срок хранения.

### 9.4. Обработка инцидентов (Incident Response)
- План реагирования на утечки, DDoS, взломы.
- Роли: координатор, техническая группа, юристы, PR.
- Время реакции (например, 15 минут на обнаружение, 1 час – на изоляцию).
- Аналитик фиксирует требования к уведомлениям (СБ, регулятор, клиенты).

### 9.5. DevSecOps и безопасность CI/CD
- SAST/DAST сканирование кода в пайплайне.
- Сканирование контейнеров на уязвимости.
- Подпись артефактов и верификация.
- Аналитик может потребовать наличие таких этапов в процессе разработки.

## 10. Пример аналитического фрагмента (для FSD)

**Функция**: авторизация платежа по карте.

**Требования безопасности**:
1. **Маскирование**: в логах и в ответах API (кроме последних 4 цифр) PAN маскируется.
2. **Шифрование**: все данные передаются по TLS 1.3, в БД – шифрование at rest.
3. **Аутентификация**: OAuth 2.0, токен передаётся в заголовке `Authorization`.
4. **Антифрод**: перед отправкой в АБС событие отправляется в антифрод; если ответ `BLOCKED` – операция отклоняется.
5. **Логирование**: логируются только `payment_id`, `order_ref`, `amount`, `status`, `timestamp`.
6. **Rate limiting**: 100 запросов в минуту на IP.
7. **Мониторинг**: метрики авторизаций, отказов, времени ответа – в Grafana.

## 12. Заключение

Информационная безопасность в банковской сфере – это не «дополнительная опция», а фундаментальный слой, пронизывающий все требования к системе. Системный аналитик должен:
- Знать основные регуляторные требования.
- Уметь формулировать требования к шифрованию, маскированию, логированию.
- Понимать, как работают антифрод-системы и DDoS-защита.
- Взаимодействовать со службой безопасности на всех этапах проекта.

Цена ошибки – утечка данных, штрафы, остановка бизнеса. Закладывайте безопасность в требования **до** разработки, а не «потом починим».
